2. **Anti-pattern.** Name one anti-pattern `test_antipatterns.py` checks for. What would break in your run if the loop used it?

A text-matching loop would have had to guess whether that prose meant "done", "waiting", or "continue" and could hang or mis-terminate; the `stop_reason` contract instead terminated deterministically on `end_turn` and the harness honestly reported `incomplete`. `test_no_integer_literal_iteration_cap_in_loop` similarly ensures my 7-turn claim_03 and 4-turn claim_08 both ran to natural completion rather than to an arbitrary cap.

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
    → Warm tier held **40** defects; the slice passed to the model was **5** (`evidence/system-4-shift-orchestrator/sql-slice-evidence.txt`, run with `--since 2026-04-20T00:00:00Z`). The query is `defects_since` in `shift_monitor/warm.py` — `SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?` — backed by the `idx_defects_shift_ts` index, called from `gather_new_defects(warm, since_ts, limit=50)` in `shift_monitor/pipeline.py`. The model never sees full history because filtering is pushed down to SQLite, which is deterministic, indexed, and free; spending model context to re-read 40 rows every shift would only grow linearly forever and give the model the job (temporal filtering) it is worst at and the database is best at.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?
    → `shift_monitor/recovery.py`, function `decide(state, now)`: resume only if the manifest has steps, is not complete, and the last step is within `STALE_RESUME_THRESHOLD_MINUTES = 30`; otherwise return `"fresh"`. The docstring pins the rationale: 30 minutes ≈ 1/16 of an 8-hour shift cycle, so inside the window the crashed session is still operating on the same working set. Past it, resuming replays a context whose premises have expired — new defects have landed (my warm tier's slice changes with every `--since` boundary), thresholds may have flipped (my run's `hot_state.json` shows `defect_rate_per_shift: ALARM`), and the transcript's intermediate reasoning is now confidently stale. A fresh session with the manifest's *findings* injected as a summary keeps the verified facts and discards the expired reasoning — cheaper and less likely to act on a dead premise. The same state-isolation discipline governs forked investigations: `fork_for_hypothesis()` in `shift_monitor/fork.py` gives each hypothesis a *copy* of `hot_state.json` in its own directory (`data/forks/<hypothesis_id>/`) plus a private `scratchpad.jsonl`, so a fork can never write to main state. I exercised this with two competing hypotheses about the 2026-04-30 capacitor-bank cluster (`evidence/system-4-shift-orchestrator/fork-isolation-evidence.txt`): the main `shift_scratchpad.jsonl` stayed at 2 lines while both forks wrote their findings, and only an explicit `merge_findings()` call brought them into the main stream (4 lines after merge) — isolation by construction, merge by decision.

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?
    → **752 bytes** after my recorded shift-C run (`evidence/system-4-shift-orchestrator/hot-state-size.txt`) against the ~5 KB budget. The hot state is re-injected into a *fresh* session every shift, forever — so its size is a permanent per-invocation tax, and any unbounded field (my run's `recent_defect_hashes` list, `active_alerts`) would compound across thousands of shifts until it crowds out the actual defect slice in the context window. The budget forces the design discipline that keeps year three as cheap as day one: bounded hashes, one-line summary, tiered everything else down into SQLite (40 rows warm) and cold storage.
